Make the next Incremendle game. Read CLAUDE.md first and follow it exactly; it's the design bar and checklist.

Music uses `.agents/skills/slopwave/SKILL.md` automatically; read `docs/music.md`
and `.slopwave/config.json`, setting up with `npm run music:setup` if needed. After
the pitch, save the game description, rolled music style and musical scale, phase,
and constraints as a brief in `.slopwave/work/<slug>/`. Keep gameplay number scale
separate. Inspect existing sessions and confirmed project preferences, author a
plan and explicit score, arrange/mix, and use `session render` for each listening
candidate. Retain exact parents, changed briefs/plans, and all revision snapshots.
Use the selected exported `song.mjs` through our existing Strudel adapter as shown
in the template; the game owns playback and state changes. Start with a composed
loop and develop it for the game's duration. Verify sampled adaptations separately
if the rolled style needs them; the session renderer supports synth voices.
Keep work, renders, feedback and preferences in this project's `.slopwave/`.
Record user feedback against the heard revision with verbatim quotes separate from
interpretations: acceptance is not pairwise preference, and only unambiguous human
comparisons establish preferences. Never label tests, agent critiques or silence as
human approval. Autonomous game delivery does not require inventing acceptance.

1. Roll the theme. Run `python3 tools/roll.py`, or `python3 tools/roll.py <seed>` if a seed is given below. It picks everything from fixed lists, each part independently and skipping what the last two weeks of games used, because an LLM asked to "come up with a game" lands on the same few ideas every time (the first three games were all about something lonely). Use exactly what it rolls; don't reroll, swap words or pick your own, because the point is to get ideas you wouldn't choose. The only exception is steering written below, which overrides the parts it names. The roll gives:
   - **theme**: subject, verb, object. The subject describes the character, not the goal, so a "lonely" or "shy" subject is still a game about the rolled drive.
   - **arc**: a drive (what the character wants), an obstacle (what's in the way), a turn (how the story lands) and an initial (the first letter of the name of the key person, place or thing). The upgrades chase the drive, push past the obstacle, and the ending lands the turn. Don't drift back to finding friends, belonging or being less lonely unless the arc itself says so.
   - **shape**: length (how long a real player takes), structure (one or more ways the progression is built; longer games roll more), twist (a wrinkle on top) and ending (the mechanical form of the finale, which the arc's turn colors). The structure is the biggest lever on how the game plays, so build the game around it and don't fall back to a straight line of upgrades with a structure theme painted on. With several structures, use them all: chain them as phases in the rolled order, or layer one inside another (a tech tree whose branches each unlock a new currency), whichever fits the arc.
   - **feel**: interaction (the core action), scale (how big the numbers get; use break_infinity.js from /shared/lib/ if it goes past 1e308), look (art style; pick fonts that suit it), palette (a Lospec palette in public/shared/palettes.json; build the whole look from its colors), music (style and scale for the background loop and every sound effect) and tone (the voice of the log lines, upgrade names and jokes).

   - **context**: usually "none". When it's a calendar nod, find something that matches the rolled kind for the release date (the day after the last entry in public/games.json, not today), search the web for it rather than going by memory (Wikipedia's page for the date is a good start for anniversaries and observances; skip brand-sponsored "National X Day" filler), and skip any topic that appears in the last 14 entries. Work it in as one small touch, never the premise; the game must make full sense to someone playing it a year later. When it's a holiday (`"kind": "holiday"`, rolled automatically when the release date is a major US holiday), lean into it: the holiday can set the scene, the look, the upgrades and the jokes, read through the rolled parts rather than replacing them (a rolled palette and look in their spookiest or most festive reading). Never use trending memes, news, politics or real people, even if the context is "none".

   If two parts fight (a reset loop in a short game, a final showdown in a cozy one), find the version where both are true, which is often the funniest one. Only if that's impossible, bend the smaller part and say so in the pitch. If it still notes a repeat of a recent game (a list too small to avoid it), keep the roll and make that part feel different anyway. Then find the logic before pitching. The roll is a pile of unrelated words, and putting them side by side isn't a story; the story is the reason they connect. Aim for a weird premise with sensible logic: the setup can be absurd internet weirdness, but once you accept it, each step should follow the way it would in real life (oaks really do make shade; shade really is cooler). A player should be able to explain why the game works the way it does in one breath, and the humor comes from taking the odd premise completely seriously.
   - List the "wait, why?" questions the roll raises (why is this character here, why would it do this to these objects, who or what is the obstacle and why).
   - Brainstorm at least five one-line explanations and pick the key idea that answers the most questions at once, where the rolled parts cause each other rather than just appear together. Words can be read loosely (repairing can be mending or restoring, a desert can be literal or a stage set) but never swapped.
   - Write the causal chain: "X wants Y because Z. The way to get it is [verb]ing [object], because… [Obstacle] gets in the way by… It ends when…, and [the turn] lands because [something planted earlier]." Every link needs a "because"; if one doesn't have it, keep looking.
   - Derive the upgrades, the twist mechanic and the jokes from the chain. Use the silly one-offs to plant the turn so the ending feels earned.
   - Hand only the pitch to a fresh subagent and ask what doesn't make sense or isn't funny. Revise once.

   Show me the roll and the chain, then pitch the game in 4–5 sentences: the premise, the core action, how the structure and twist play out, what the music sounds like, and how it ends. Make it play differently from the games already in public/, not a reskin. Then build it without waiting for approval.

2. Build it as public/<slug>/index.html, where slug is the title in lowercase with hyphens, starting from templates/game.html. Set data-day to the next "n" in public/games.json; numbers are internal ids only, so never show them to players. It needs:
   - the rolled interaction as the core action, understood within five seconds, working with both mouse and touch
   - the rolled structure and twist as real mechanics, with saves that resume mid-game (phase, layer, resets and all)
   - for short and story games, offline progress: when a player comes back, credit the time away (capped, at a reduced rate) and tell them what happened while they were gone
   - pleasant synthesized Web Audio sounds for every action, an unlock chime, a purchase sound and a finale, all on the rolled musical scale, (no sound buttons of your own: the site's Sound panel handles volume and mute)
   - background music in the rolled style, composed with slopwave from the saved game brief and plan, exported through public/shared/kit/music.mjs with instruments that suit the style (`npm run samples -- list`; fetch sampled instruments you use): quiet and under the sound effects in the mix. Develop the initial composed loop with deliberate motif, harmony and texture variations so the finished soundtrack does not repeat every few seconds. Shift key, tempo or tone subtly as the game moves through phases; the existing adapter starts on the first gesture and keeps playing in a background tab. Verify the exported module with `npm run music:check -- <revision/song.mjs>`, then listen over several returns in the game and check phase transitions; numerical checks alone cannot establish musical quality.
   - an upgrade column on the right (stacking below on phones) where new unlocks pulse with a "new" tag and the heading shows how many are affordable. On desktop it's sticky, no taller than the window, and short enough that it doesn't scroll at the busiest point of the game: goals on their meters, repeat actions (the prestige, a booth) at the top of the column, upgrades as compact cells two to a row with the details in a tooltip in the game's look, and one tab per currency once there's more than one to spend (see CLAUDE.md). Nothing you press starts below the fold. Plan this from the start for games with several currencies or many producers, not after the column overflows
   - a mix of real upgrades and a few silly one-offs that add story, a meter that tracks progress toward the arc's drive, and flavor text in a log line, all written in the rolled tone
   - a real ending in the rolled ending form that calls DailyGame.finish() once with short, emoji-led share lines, plus a Share button
   - the rolled look in the rolled palette, done properly (Google Fonts self-hosted with `npm run fonts -- <slug>`, canvas art), not a copy of the earlier games. Fetch source shapes with `npm run art` and restyle them with public/shared/kit/sprites.mjs and fx.mjs (recolor, gradient, pixelate, outline, rough redraw, halftone…) so they look like this game, not like the icon set. Draw main characters by hand. Register every sprite, open the game with `?sprites`, look at the sheet, and fix anything that reads badly before building around it
   - start from the template: sound effects and music on public/shared/kit/audio.mjs, the economy in its own module next to index.html so the pacing sim imports the real rules
   - credits: `npm run credits -- <slug>` once the art, libraries, fonts and palette are settled
   - a `why.json` for the top bar's "What??" panel (step 7 of CLAUDE.md's checklist): every roll, including subject, verb and object, with a line or two on what the game made of it. Write it from the pitch's "wait, why?" answers: the logic that connects the rolls is the fun part, told in the game's own names and jokes. Ending rows marked as spoilers

3. Check the pacing before you call it done. Write a quick headless sim of a reasonable player: one manual action every ~1.3s, buying the cheapest affordable upgrade, and playing the structure the way a person would (resetting when the bonus is worth it, picking a sensible branch, arranging space greedily, keeping up with decay). Real players take longer than the sim, so pick a target length inside the rolled range, say it in the pitch, and tune costs until the sim finishes in about 70–80% of it. For short and story games, simulate sittings: 20–40 minutes of play, a few hours away with offline progress, repeat, and report both the time played and the number of sittings. Err long rather than short: an incremental that ends just as it gets good isn't worth starting. Length has to come from content, not slower prices: more upgrades, more layers, new mechanics that unlock along the way, so there's still something to buy every 15–30 seconds. Aim for a purchase every 15–30 seconds; in long games the gap can stretch to 60 seconds late in a phase, as long as something else is going on. No dead stretches anywhere. Show me the purchase timeline, with phase or reset boundaries marked.

4. Test it in a real browser. Add the game's busy mid-game save to tools/cards.json first (step 8 of CLAUDE.md's checklist), then run `npm run check -- <slug>` (first time on a machine: `npm install && npm run setup`). It checks that the ending and upgrades are hidden at the start, that the upgrade column and every play-area button fit in the window with the mid-game save, that the What?? panel opens and hides its spoilers, that a Save panel code loads in a fresh browser, plays the opening, loads a finished save to check the ending and share card, checks for sideways scroll at 390px, and fails on console errors. Run `npm run mix -- <slug>` with a save for each phase and fix the levels until music sits near -24 dBFS and every effect peaks near -10 (show me the table). Also check that sound starts only after a gesture, and that a mid-game save (mid-phase or after a reset) resumes correctly. It relies on the conventions in CLAUDE.md (`#ending`, `#shareBtn`, upgrades as buttons in `#shop`, a save with `ended: true` resuming into the ending). Then look at every screenshot in tests/screenshots/ (including the sprite sheet, the credits panel and the What?? panel) and fix anything that looks off. If the core interaction needs more than the script's generic drag-and-tap, play it with a short Playwright script of your own. For games with phases, load a save at the start of each phase, play that phase's action for real, and screenshot it; then buy the final upgrade live to watch the real ending.

5. Add the entry to public/games.json, dated the day after the last one, with n, slug, title, tagline, emoji, scale and minutes (from the rolled length), plus `seed` and every rolled field except subject, verb and object, copied as is (`interaction`, `arc`, `length`, `structure`, `twist`, `ending`, `look`, `music`, `tone`, `context`, `palette`; for a calendar nod, add `"topic"` to the context saying what it was, e.g. `"first frost"`; a holiday context is already complete), so the next roll can avoid repeating it. Rerun `npm run credits -- <slug>` (it picks up the palette from the entry). Make sure the card save from step 4 is a busy mid-game moment that doesn't spoil the ending, run `npm run og` to render its social card and refresh the landing card, look at public/<slug>/og.png to check it gives nothing away, and rerun `npm run check -- <slug>`. Commit with a message naming the game and its seed.
