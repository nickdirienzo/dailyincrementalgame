description: Roll a theme and build the next Daily Incremental game, with a pacing sim and browser test
argument-hint: "[optional steering, e.g. \"Use seed 12345\" or \"Make the interaction catch-falling-things\"]"
---

Make the next Daily Incremental game. Read CLAUDE.md first and follow it exactly; it's the design bar and checklist.

1. Roll the theme. Run `python3 tools/roll.py`, or `python3 tools/roll.py <seed>` if a seed is given below. It picks everything from fixed lists, each part independently, because an LLM asked to "come up with a game" lands on the same few ideas every time (the first three games were all about something lonely). Use exactly what it rolls; don't reroll, swap words or pick your own, because the point is to get ideas you wouldn't choose. The only exception is steering written below, which overrides the parts it names. The roll gives:
   - **theme**: subject, verb, object. The subject describes the character, not the goal, so a "lonely" or "shy" subject is still a game about the rolled drive.
   - **arc**: a drive (what the character wants), an obstacle (what's in the way), a turn (how the story lands) and an initial (the first letter of the name of the key person, place or thing). The upgrades chase the drive, push past the obstacle, and the ending lands the turn. Don't drift back to finding friends, belonging or being less lonely unless the arc itself says so.
   - **shape**: length (how long a real player takes), structure (one or more ways the progression is built; longer games roll more), twist (a wrinkle on top) and ending (the mechanical form of the finale, which the arc's turn colors). The structure is the biggest lever on how the game plays, so build the game around it and don't fall back to a straight line of upgrades with a structure theme painted on. With several structures, use them all: chain them as phases in the rolled order, or layer one inside another (a tech tree whose branches each unlock a new currency), whichever fits the arc.
   - **feel**: interaction (the core action), scale (how big the numbers get), look (art style; pick a palette and fonts that suit it), music (style and scale for the background loop and every sound effect) and tone (the voice of the log lines, upgrade names and jokes).

   - **context**: usually "none". When it's a calendar nod, find something that matches the rolled kind for the release date (the day after the last entry in public/games.json, not today), search the web for it rather than going by memory (Wikipedia's page for the date is a good start for anniversaries and observances; skip brand-sponsored "National X Day" filler), and skip any topic that appears in the last 14 entries. Work it in as one small touch, never the premise; the game must make full sense to someone playing it a year later. Never use trending memes, news, politics or real people, even if the context is "none".

   If two parts fight (a reset loop in a 5-minute game, a final showdown in a cozy one), find the version where both are true, which is often the funniest one. Only if that's impossible, bend the smaller part and say so in the pitch. If it notes a repeat of a recent game, keep the roll and make that part feel different anyway. Show me the roll, then pitch the game in 4–5 sentences: the premise, the core action, how the structure and twist play out, what the music sounds like, and how it ends. Make it play differently from the games already in public/, not a reskin. Then build it without waiting for approval.

2. Build it as public/<slug>/index.html, where slug is the title in lowercase with hyphens, starting from templates/game.html. Set data-day to the next "n" in public/games.json; numbers are internal ids only, so never show them to players. It needs:
   - the rolled interaction as the core action, understood within five seconds, working with both mouse and touch
   - the rolled structure and twist as real mechanics, with saves that resume mid-game (phase, layer, resets and all)
   - pleasant synthesized Web Audio sounds for every action, an unlock chime, a purchase sound and a finale, all on the rolled musical scale, plus a sound toggle using the `di:sound-muted` key
   - background music in the rolled style, generated live with Web Audio (no audio files): a quiet loop with slow chord changes and some variation, under the sound effects in the mix, starting on the first gesture, pausing while the tab is hidden, with its own toggle using `di:music-muted` (sound off silences it too). For longer games, let it change with the phases.
   - an upgrade column on the right (stacking below on phones) where new unlocks pulse with a "new" tag and the heading shows how many are affordable
   - a mix of real upgrades and a few silly one-offs that add story, a meter that tracks progress toward the arc's drive, and flavor text in a log line, all written in the rolled tone
   - a real ending in the rolled ending form that calls DailyGame.finish() once with short, emoji-led share lines, plus a Share button
   - the rolled look, done properly (palette, Google Fonts, canvas art), not a copy of the earlier games

3. Check the pacing before you call it done. Write a quick headless sim of a reasonable player: one manual action every ~1.3s, buying the cheapest affordable upgrade, and playing the structure the way a person would (resetting when the bonus is worth it, picking a sensible branch, arranging space greedily, keeping up with decay). Real players take longer than the sim, so tune costs until it finishes in about 60–70% of the rolled length (6–9 minutes for 10–15, 13–20 for 20–30, 30–40 for 45–60). Aim for a purchase every 15–30 seconds; in long games the gap can stretch to 60 seconds late in a phase, as long as something else is going on. No dead stretches anywhere. Show me the purchase timeline, with phase or reset boundaries marked.

4. Test it in a real browser. Run `npm run check -- <slug>` (first time on a machine: `npm install && npm run setup`). It checks that the ending and upgrades are hidden at the start, plays the opening, loads a finished save to check the ending and share card, checks for sideways scroll at 390px, and fails on console errors. Also check that music and sound start only after a gesture, that both toggles work and persist, and that a mid-game save (mid-phase or after a reset) resumes correctly. It relies on the conventions in CLAUDE.md (`#ending`, `#shareBtn`, upgrades as buttons in `#shop`, a save with `ended: true` resuming into the ending). Then look at every screenshot in tests/screenshots/ and fix anything that looks off. If the core interaction needs more than the script's generic drag-and-tap, play it with a short Playwright script of your own.

5. Add the entry to public/games.json, dated the day after the last one, with n, slug, title, tagline, emoji, scale and minutes (from the rolled length), plus `seed` and every rolled field except subject, verb and object, copied as is (`interaction`, `arc`, `length`, `structure`, `twist`, `ending`, `look`, `music`, `tone`, `context`; for a calendar nod, add `"topic"` to the context saying what it was, e.g. `"first frost"`), so the next roll can flag repeats. Then run `npm run og` to render its social card and refresh the landing card, look at public/<slug>/og.png, and rerun `npm run check -- <slug>`. Commit with a message naming the game and its seed.
